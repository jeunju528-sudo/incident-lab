## 세운 가설과 검증 결과
1. settle-api 배포·설정 변경 — 배포 이력, 설정 이력 — 배제 — 11/12 이후 변경 없음
2. 특정 SQL 지연 — APM trace, Top Slow SQL — 확정 — 7k2mq9xv1fz3d 평균 8,011ms
3. DB 락 경합 — V$SESSION, V$LOCK — 배제 — 블로킹 세션 없음, 대기 이벤트가 User I/O
4. 통계 정보 노후 — DBA_TAB_STATISTICS, DBA_TAB_MODIFICATIONS — 확정 — NUM_ROWS 1,204 vs 실제 4,187만 건

## 근본 원인
1. 왜 응답이 느렸나? → 7k2mq9xv1fz3d가 IX_STXN_STATUS(값 4종류)로 약 4천만 건을 단일 블록 읽기로 스캔했다.
2. 왜 그 인덱스를 골랐나? → 옵티마이저가 테이블을 1,204건으로 알고 있어 결과를 1건으로 추정했다.
3. 왜 통계가 1,204건이었나? → 11/15 21:30 시작된 SETTLEMENT_TXN 재적재 도중, 22:04에 자동 통계 수집 Job이 실행됐다.
4. 왜 적재 후에도 갱신되지 않았나? → 재적재 배치에 통계 수집 단계가 없었다.
5. 왜 아침에 터졌나? → 기존 정상 커서가 자동 무효화(AUTO_INVALIDATE)되면서 08:10경 재파싱됐고, 이때 잘못된 통계로 새 실행계획이 만들어졌다.

## 완화 조치와 근본 해결
- 완화: 없음 (통계 재수집으로 바로 진행)
- 해결: SETTLEMENT_TXN 통계 재수집 (DBMS_STATS.GATHER_TABLE_STATS, cascade => TRUE)
- 참고: 기본 옵션(no_invalidate => AUTO_INVALIDATE)으로 수집해 기존 커서가 즉시 교체되지 않았고, 수집 완료 후 정상화까지 14분이 더 걸렸다.

## 재발 방지
- [ ] 재적재 배치 마지막 Step에 통계 수집 추가 (GATHER_TABLE_STATS, no_invalidate => FALSE) — 정산팀
- [ ] 재적재 시작 시 통계 잠금(LOCK_TABLE_STATS), 종료 후 해제·수집 — 정산팀 + DBA
- [ ] 재적재 작업은 자동 통계 수집 Window(22:00~)와 겹치지 않게 스케줄 조정 — DBA
- [ ] 주요 SQL의 plan_hash_value 변경 + 평균 수행시간 급증 시 알람 — DBA + 온콜
- [ ] 장애 대응 런북에 "실행계획 고정(SPM) 요청 절차" 추가 — 온콜

## 유사 장애 확인 절차 (평소 빠르던 쿼리가 갑자기 느려졌을 때)
1. 공지: 영향 범위 확인 후 1차 공지 (원인 확인 전이라도)
2. 변경점: 앱 배포·설정 이력 + DB 쪽 변경(배치, 데이터 이관, DBA 작업, 통계 수집 이력)
3. 원인 SQL 특정: APM Top Slow SQL 또는 V$SQL에서 sql_id 확인
4. 대기 이벤트로 방향 잡기: V$SESSION 집계
   - User I/O(db file sequential read) → 실행계획 문제 의심
   - enq: TX - row lock contention → 락 의심
5. 실행계획 확인: DBMS_XPLAN.DISPLAY_CURSOR → 추정 Rows가 비정상적으로 작은데 실제로 느리면 통계 의심
6. 계획 변경 여부: DBA_HIST_SQLSTAT에서 plan_hash_value가 언제 바뀌었는지 확인
7. 통계 확인: DBA_TAB_STATISTICS(NUM_ROWS, LAST_ANALYZED, STALE_STATS) vs DBA_TAB_MODIFICATIONS 또는 실제 건수
8. 완화: 이전 정상 계획을 SQL Plan Baseline으로 고정 (DBA 요청)
9. 해결: 통계 재수집 (no_invalidate => FALSE), 부하 시간대면 DBA와 시점 협의 
10. 사후: Baseline 해제 여부 검토, 공지 종료

- 놓친 단서: 실행계획의 추정 Rows 1과 실제 응답시간의 괴리, 대기 이벤트가 User I/O였는데 락부터 확인, 전날 밤 테이블 재적재 작업(변경점) 미확인
