## 세운 가설과 검증 결과

## 근본 원인
5 Whys
1. 왜 전체 서비스가 503이었나?
   → LB가 shop-api 4대를 모두 health check 실패로 제외했다.
2. 왜 health check가 실패했나?
   → `/actuator/health`가 업무 요청과 같은 Tomcat 스레드 풀(200개)을 쓰는데, 남는 스레드가 없어 2초 안에 응답하지 못했다.
3. 왜 스레드가 고갈됐나?
   → 결제(checkout) 요청 스레드가 NexPay 승인 API 응답을 무한정 기다리며 반환되지 않았다.
4. 왜 무한정 기다렸나?
   → 결제 클라이언트에 Read Timeout이 없었다. v2.14.0(11/17) #321에서 외부 API 클라이언트를 공통 RestTemplate Bean으로 통합하면서 `new RestTemplate()` 기본값(SimpleClientHttpRequestFactory, connect/read timeout 무한)이 적용됐다. 기존 NexPayClient의 전용 설정(readTimeout 5s)은 사라졌다.
5. 왜 이 변경이 걸러지지 않았나?
   → 외부 연동 타임아웃에 대한 리뷰 체크리스트와 테스트가 없었다. 평소 NexPay는 600~700ms로 응답했기 때문에 기능 테스트에서는 문제가 드러나지 않았다.

구조적 원인
- 격리 부재: 결제 한 기능의 외부 의존성 장애가 같은 스레드 풀을 쓰는 전 기능으로 번졌다 (Bulkhead 없음).
- 차단 장치 부재: 외부 장애를 감지해 호출을 멈추는 Circuit Breaker가 없었다. 타임아웃이 없어 Circuit Breaker가 있었더라도 동작하지 않았을 것이다.
- 헬스체크 설계: 업무 트래픽 포화가 곧 "서버 죽음"으로 판정되어, 정상 기능까지 LB에서 빠졌다.
- 정보 전달 실패: NexPay의 사전 안내(19:29)가 담당자가 보지 않는 그룹 메일로만 수신됐다.

## 완화 조치와 근본 해결
- 완화 (장애 중, 실무 정석 기준)
  1. jstack 3회 채취로 증거 보존 (재기동 전)
  2. Nginx에서 `/api/orders/checkout`만 503 + "결제 일시 점검" 응답으로 차단 → 새 요청이 스레드를 다시 잡지 않게 함
  3. shop-api 롤링 재기동으로 묶인 스레드 해제 → 메인/상품/검색 복구 확인
  4. 공지 업데이트: "결제만 일시 중단, 나머지 정상"
  5. 결과 불명 318건 대사: NexPay 조회 API로 승인 여부 확인 → 승인 건은 주문 보정 또는 망취소, 미승인 건은 FAILED 처리 → CS팀에 대상 고객 목록 전달
  6. NexPay 복구 확인 후 타임아웃 핫픽스 배포, 결제 차단 해제
- 근본 해결
  - 결제 클라이언트 타임아웃 명시: connectTimeout 1s, readTimeout 5s (NexPay SLA 3초 + 여유)
  - 공통 RestTemplate Bean 폐기 → 연동별 전용 클라이언트(타임아웃·풀 크기 개별 설정)
  - Resilience4j Circuit Breaker 적용 (slow-call 3s, 실패율 50%, OPEN 30s) + fallback으로 "결제 일시 점검" 응답
  - Bulkhead 적용: 결제 외부 호출 동시 실행 수 제한 (예: 30) → 나머지 스레드는 다른 API용으로 보장
  - 결제 타임아웃 시 FAILED가 아닌 UNKNOWN 상태로 저장, 조회 API로 자동 재확인하는 보정 잡 추가
  - health check를 별도 포트로 분리 (`management.server.port=8081`), LB는 liveness만 확인

## 회고
- 잘한 점: 재기동 보류로 증거 보존, 공지 선행, APM 구간 분해로 DB·검색 가설을 빠르게 배제, 외부 상태 페이지와 curl -w로 외부 원인을 직접 확인
- 놓친 단서: busy threads 포화 + CPU 정상 신호, 배포 #321(공통 RestTemplate 통합), Read Timeout 설정 미확인, 결과 불명 결제 건, NexPay 사전 안내 메일
- 다음에 더 빨리 가려면: 스레드 포화 알람 → jstack 먼저 → 대기 대상 확인 → 기능 차단 + 재기동

## 유사 상황 확인 절차
1. 스레드 풀 포화인데 CPU·메모리가 정상인가? → I/O 대기로 판단하고 재기동 전에 jstack 1회
2. 스레드가 대기하는 대상은 무엇인가? (외부 HTTP / DB 커넥션 / 락)
3. 외부 의존성이면: 상태 페이지 → curl -w로 구간 측정(dns/connect/tls/ttfb)
4. 우리 클라이언트 설정 확인: connect/read timeout, 재시도 정책, 커넥션 풀 크기
5. 최근 외부 연동 코드·설정 변경 이력 (당일 배포만 보지 말 것)
6. 완화: 해당 기능 차단 → 재기동 → 나머지 기능 복구 확인 → 공지 업데이트
7. 결과 불명 거래 대사 (상대 시스템 조회 API, 망취소)
8. 협력사 공지 채널(메일·상태 페이지) 수신 여부 점검
