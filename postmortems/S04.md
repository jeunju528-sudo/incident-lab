## 세운 가설과 검증 결과
1. 앱과 DB가 같은 서버에 있어 자원 경합 — CMDB 구성 조회 — 배제 — 앱 서버와 DB 서버가 분리돼 있음
2. 특정 SQL의 실행계획 문제 — APM 트레이스, `DBMS_XPLAN.DISPLAY_CURSOR` — 배제 — INSERT 실행계획은 정상(LOAD TABLE CONVENTIONAL). 실행이 아니라 대기가 문제
3. DB 락 — `V$SESSION`, `V$LOCK` — 확정 — `enq: TM - contention` 127세션, 블로커 SID 412가 TB_AUDIT_LOG에 TM 모드 6 보유
4. 최근 배포 영향 — 배포 이력 — 배제 — 장애 시각과 겹치는 관련 서비스 배포 없음
5. 작업자가 DML 후 커밋하지 않음 — 작업자 확인 — 배제 — DELETE는 커밋 완료. 실제로 막고 있던 문장은 `ALTER TABLE ... MOVE`(DDL)

## 근본 원인
`ALTER TABLE ... MOVE`(ONLINE 옵션 없음)는 실행되는 동안 테이블에 TM 모드 6(Exclusive) 락을 잡는다. INSERT·UPDATE·DELETE는 테이블에 TM 모드 3(Row-X)을 요청하는데, 모드 6과는 호환되지 않는다. 그래서 TB_AUDIT_LOG에 감사 로그를 남기는 모든 쓰기 트랜잭션이 `enq: TM - contention`으로 대기했다. SELECT는 TM 락을 잡지 않으므로 조회는 처음에 정상이었다. 이후 대기 중인 요청들이 DB 커넥션을 쥔 채 기다리면서 Hikari 풀이 고갈됐고, 조회 API까지 지연됐다.

5 Whys
1. 왜 쓰기 API가 멈췄나? → 모든 쓰기 트랜잭션이 커밋 시점에 TB_AUDIT_LOG INSERT에서 대기했다.
2. 왜 INSERT가 대기했나? → SID 412가 TB_AUDIT_LOG에 TM 모드 6을 잡고 있어 모드 3을 얻을 수 없었다.
3. 왜 모드 6이 잡혔나? → 운영팀이 공간 회수를 위해 ONLINE 옵션 없이 `ALTER TABLE ... MOVE`를 실행했다.
4. 왜 운영 시간에 실행됐나? → 23시 예정 변경 건이었지만, 작업자가 DELETE가 빨리 끝나자 MOVE를 미리 실행했다. 승인된 시간 외 실행을 막는 통제가 없었다.
5. 왜 감사 로그 하나가 전체 쓰기 장애로 번졌나? → 감사 로그 INSERT가 본 업무와 같은 트랜잭션에 묶여 있고(common-audit), 세 서비스가 같은 테이블을 공유한다. 쿼리 타임아웃이 없어 대기가 무한정 이어졌다.

부가 원인(중복 주문)
- 고객에게는 Nginx가 30초에 504를 반환했지만, 서버 쪽 트랜잭션은 계속 대기하다가 14:17 락 해제 후 그대로 커밋됐다.
- 고객은 실패로 알고 재시도해 같은 주문이 2건 생성됐다. 주문 API에 멱등성 보장이 없었다.

## 완화 조치와 근본 해결
- 완화
  - 블로커 세션(SID 412)을 KILL해 TM 락을 해제했다. DDL은 중간에 중단되면 롤백되므로 테이블 데이터에는 영향이 없다.
  - 14:18 대기 이벤트 0건, 14:19 전 서비스 지표 정상화를 확인했다.
  - 장애 공지를 게시하고 정상화 후 해제했다.
- 근본 해결
  - 23시 예정 작업을 같은 스크립트로 진행하지 않도록 중단하고, 방식을 바꿔 다시 일정을 잡는다.
    - 19c Enterprise Edition: `ALTER TABLE TB_AUDIT_LOG MOVE ONLINE UPDATE INDEXES`
    - ONLINE을 쓸 수 없는 환경: 서비스 점검 공지 후 점검 창에서 실행하고, 실행 후 `UPDATE INDEXES` 또는 인덱스 REBUILD로 UNUSABLE 상태를 남기지 않는다.
    - DBA 검토와 승인을 받아 CHG-20261118-07에 반영한다.
  - 중복 주문: 14:05~14:19 사이 동일 회원·동일 상품 주문 목록과 결제 상태를 추출해 주문/결제 담당팀에 이관하고, 중복 건을 취소·환불한다. CS팀에는 확인 후 개별 안내하도록 안내 문구를 전달한다.

## 재발 방지
- [ ] 프로세스: 운영 시간대 DDL 금지. 변경 건은 승인된 시간 외에 실행할 수 없도록 하고, 대용량 테이블 DDL은 DBA 사전 검토를 필수로 한다. (담당: 운영팀, DBA)
- [ ] 프로세스: 변경 작업 체크리스트에 "락 모드 / ONLINE 가능 여부 / 인덱스 영향 / 예상 소요 시간" 항목을 추가한다. (담당: DBA)
- [ ] 모니터링: 블로킹 세션이 30초 이상 지속되면 알람을 보낸다(`enq: TM - contention`, `enq: TX - row lock contention`). (담당: DBA, 플랫폼팀)
- [ ] 모니터링: 운영 DB에 SQL Developer 등 개인 툴로 DDL을 실행하면 감사 알림을 보낸다. (담당: DBA)
- [ ] 설정: JDBC 쿼리 타임아웃을 Nginx 업스트림 타임아웃(30초)보다 짧게 설정해, 클라이언트가 실패를 받은 뒤 서버 트랜잭션이 늦게 커밋되는 일을 막는다. (담당: 각 서비스)
- [ ] 코드: 감사 로그 기록을 비동기 처리하거나 별도 트랜잭션으로 분리해, 감사 로그 장애가 본 업무를 막지 않게 한다. (담당: 플랫폼팀, common-audit)
- [ ] 코드: 주문·포인트 사용 API에 멱등 키(Idempotency-Key)를 적용해 재시도해도 중복 처리되지 않게 한다. (담당: 주문팀, 포인트팀)

## 유사 상황 확인 절차 (테이블 락 의심 시)
1. APM에서 느린 요청들의 공통 SQL과 공통 테이블을 찾는다.
2. 실행계획으로 "느린 실행"인지 "대기"인지 구분한다. A-Time이 짧은데 응답이 길면 대기다.
3. `V$SESSION`에서 EVENT와 BLOCKING_SESSION을 보고 최상위 블로커를 찾는다.
4. `V$LOCK`에서 블로커의 TYPE과 LMODE를 본다.
   - TX 6 + 블로커 INACTIVE(SQL*Net message from client) → 미커밋 DML
   - TM 6 + 블로커 ACTIVE(direct path read 등) → DDL(MOVE, TRUNCATE, 인덱스 생성 등)
5. `V$SQL`에서 블로커의 SQL_ID 텍스트를 확인한다. 무엇을 끊는지 알고 끊는다.
6. 앱 배포 이력과 함께 DB 변경 작업 이력(CHG), 배치 실행 이력을 확인한다.
7. 작업자에게 통보한 뒤 블로커를 KILL하고, 대기 이벤트가 0이 됐는지와 지표 회복을 확인한다.
8. 장애 시간대에 지연 커밋된 트랜잭션(중복 주문, 중복 결제)을 추출해 담당팀에 이관한다.
9. 같은 작업을 다시 실행하기 전에 방식(ONLINE 옵션, 점검 창)과 승인 여부를 확인한다.
