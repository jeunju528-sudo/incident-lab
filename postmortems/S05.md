## 근본 원인
- 직접 원인: v3.7.0(#412) SettlementReportService.exportCsv()가 DataSource에서 직접 커넥션을 얻은 뒤, rs/ps/conn의 close()를 try 블록의 정상 경로에만 두었다. 쿼리 실행(88행)에서 예외가 나면 catch로 바로 넘어가 커넥션이 풀에 반납되지 않았다(Connection Leak).
- 트리거: 일부 판매자 데이터에서 ORA-01722(invalid number)가 발생해 리포트 다운로드가 실패했고, 실패할 때마다 커넥션이 1개씩 누수됐다.
- 지연 발현: 백오피스 전용 기능이라 호출 빈도가 낮았다. 인스턴스당 풀 20개가 다 새는 데 배포 후 약 70분이 걸렸고, 3대가 17:41~17:46에 차례로 고갈됐다.
- 5 Whys
  1. 왜 주문 API가 실패했나 → 모든 요청이 커넥션 획득 대기 30초 후 타임아웃
  2. 왜 커넥션이 없었나 → 리포트 기능이 예외 경로에서 커넥션을 반납하지 않음
  3. 왜 반납 코드가 예외 경로에 없었나 → 자원 반납을 수동 코드로 처리했고, try-with-resources나 JdbcTemplate을 쓰지 않음
  4. 왜 배포 전에 못 잡았나 → 스테이징은 정상 데이터로만 테스트, 리뷰는 성능 관점만 확인, 정적 분석 규칙 없음
  5. 왜 장애가 주문까지 번졌나 → 리포트와 주문이 같은 커넥션 풀을 공유했고, 누수 탐지와 풀 고갈 알람이 없었음

## 완화 조치와 근본 해결
- 완화: 확인 중 공지, Nginx 5xx 시 점검 JSON 응답 적용, v3.6.3 롤백(재기동으로 누수 커넥션 정리)
- 해결
  - exportCsv()를 JdbcTemplate.queryForStream(또는 RowCallbackHandler)으로 바꿔 자원 반납을 프레임워크에 맡김. 직접 JDBC가 꼭 필요하면 try-with-resources를 쓰고 예외 시 rollback
  - ORA-01722 원인 데이터(형 변환 대상 컬럼) 수정, 해당 판매자 케이스를 테스트 데이터로 추가
  - 수정본을 재배포하고 #415 쿠폰 문구를 다시 반영
