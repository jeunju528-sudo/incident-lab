## 근본 원인
1. 왜 결제가 실패했나: approve·cancel 트랜잭션의 UPDATE MERCHANT_BALANCE가 3초 트랜잭션 타임아웃(@Transactional(timeout = 3))을 넘겨 QueryTimeoutException이 발생했다.
2. 왜 UPDATE가 3초를 넘겼나: 같은 가맹점 행을 정산 배치 세션(SID 812)이 Exclusive 락(TX, LMODE 6)으로 잡고 있어 enq: TX - row lock contention으로 대기했다.
3. 왜 배치가 락을 오래 잡았나: SettlementAggregateJob.run() 전체가 하나의 @Transactional로 묶여 있어, 맨 앞의 markSettling UPDATE로 대상 가맹점 12,408개 행에 락을 건 뒤 PAYMENT_TXN 대용량 집계가 끝날 때까지 약 60초 동안 COMMIT하지 않았다.
4. 왜 오늘 처음 문제가 됐나: 기존에는 결제가 거의 없는 02:00에 하루 1회만 실행돼 경합이 드러나지 않았다. v1.8.0(SETL-221)에서 실시간 대시보드 요구로 주기를 3분으로 바꾸면서 낮 시간 결제 트래픽과 3분마다 겹치게 됐다.
5. 왜 이 변경이 그대로 운영에 나갔나: 배치 변경 리뷰가 배치팀 내부에서만 이뤄졌고, 같은 테이블을 온라인으로 갱신하는 payment-api 측 영향(락 범위, 실행 시간, 실행 시간대)을 검토하는 절차가 없었다. 주기 변경이 설정값(cron) 수정이라 성능·부하 검증 대상에서도 빠졌다.

## 완화 조치와 근본 해결
- 완화: settle-batch를 v1.7.3으로 롤백해 실행 주기를 매일 02:00으로 되돌림(14:31 시작, 14:40 완료). CS팀에 결제 지연 안내 공지 요청(14:16).
- 개선했어야 할 완화: 원인 확인 직후 스케줄러에서 SettlementAggregateJob을 일시정지했다면 1분 안에 재발을 막을 수 있었다. 롤백 배포 대기 10분 동안 배치가 4회 더 실행되며 실패가 이어졌다.
- 근본 해결:
  - SettlementAggregateJob의 트랜잭션 범위를 분리한다. 대용량 집계(SELECT)는 트랜잭션 밖 또는 읽기 전용 트랜잭션에서 먼저 수행하고, MERCHANT_BALANCE 갱신은 가맹점 청크(예: 500건) 단위로 짧게 커밋한다.
  - 락을 거는 UPDATE를 트랜잭션 맨 끝으로 옮겨 락 보유 시간을 최소화한다.
  - 실시간 대시보드 요구는 MERCHANT_BALANCE를 갱신하지 않는 별도 집계 테이블(또는 조회 전용 집계)로 충족해, 온라인 결제가 갱신하는 행과 배치가 갱신하는 행을 분리한다.
  - 분리 전까지는 주기 단축 배포를 보류한다.

- [ ] 프로세스: 장애 대응 런북에 "주기적 블로커는 KILL 전에 발생원(스케줄)부터 정지" 항목 추가

## 회고
- 잘한 점: 배포·실행계획·통계·외부 연동 가설을 근거를 들어 하나씩 배제했다. V$SESSION·V$LOCK으로 블로커를 특정하고, 블로커의 정체에서 배치 배포 이력까지 추적해 원인을 확정했다. 고객 영향이 커지기 전에 CS 공지를 요청했다.
- 놓친 단서: 변경점을 payment-api 배포에서만 찾고 같은 DB를 쓰는 배치 배포를 늦게 확인했다. 실행계획에서 인덱스 스캔 0.01초 대비 전체 2.97초의 차이(대기 신호)와 APM의 3분 주기 몰림을 스스로 연결하지 못했다(힌트 2회). APM External 열과 PG-Monitor로 이미 배제된 KCP 구간을 다시 확인했다. "락 전부 KILL"로 대상을 특정하지 않고 요청했다. 팀장 문의에 상황을 공유하지 않았다.
- 다음에 더 빨리 가려면: QueryTimeoutException을 보면 바로 DB 대기 이벤트(V$SESSION)를 확인한다. 느린 요청의 시각 분포에서 주기성을 먼저 본다. 원인 확인 즉시 발생원 정지(잡 일시정지)로 완화하고, 롤백·근본 해결은 그 뒤에 한다. 15~30분 간격으로 팀장·CS에 영향 범위, 원인, 복구 예상 시각을 공유한다.

## 다음에 비슷한 상황에서 확인할 절차 (DB 대기형 간헐 타임아웃)
1. 영향 범위: 특정 서버만인지 전체 서버인지, 특정 API만인지 확인한다. 전체 서버 공통이면 앱 서버보다 공유 자원(DB, 외부 연동)을 먼저 의심한다.
2. 시간 패턴: APM에서 느린 요청 시각을 정렬해 주기성(N분마다, 정각마다)이 있는지 본다. 주기성이 있으면 배치·스케줄러·크론을 1순위로 둔다.
3. 변경점: 내 서비스 배포뿐 아니라 같은 DB를 쓰는 다른 서비스·배치의 배포, DDL, 스케줄 변경을 장애 시작 30분 전부터 확인한다.
4. 일이 많아서 느린지, 기다려서 느린지 구분: 실행계획의 Cost·A-Rows·Buffers는 작은데 A-Time만 크면 대기다. 대기라면 V$SESSION의 EVENT로 무엇을 기다리는지 본다.
5. 락 대기(enq: TX - row lock contention)라면 블로커를 찾는다:
   - SELECT sid, serial#, machine, program, module, event, blocking_session, final_blocking_session, sql_id, prev_sql_id FROM gv$session WHERE blocking_session IS NOT NULL;
   - 블로커의 현재 SQL이 락과 무관해 보이면 prev_sql_id와 같은 트랜잭션 안의 앞선 DML을 본다.
6. 블로커의 주인(배치·서비스·담당자)을 확인하고, KILL 전에 영향(롤백되는 작업, 재실행 여부)을 담당자와 합의한다. KILL은 블로커 하나만, ALTER SYSTEM KILL SESSION 'sid,serial#,@inst_id' IMMEDIATE.
7. 블로커가 주기적으로 다시 생기는 구조라면 KILL만으로는 끝나지 않는다. 스케줄 일시정지 또는 원인 변경 롤백으로 재발을 먼저 막는다.
8. 완화 후 다음 주기 시각을 넘겨서도 알람이 없는지, 락 대기 세션이 0인지 확인하고 해소를 선언한다.
9. 진행 중에 팀장·CS에 영향 범위, 원인 추정, 복구 예상 시각을 15~30분 간격으로 공유한다.
